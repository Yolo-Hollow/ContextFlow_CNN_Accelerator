\chapter{数据流与分块调度优化}
\label{chap:dataflow}

本章讨论本文针对真实 YOLOv3-tiny 层提出的数据流与调度优化。若只考虑阵列峰值，卷积层似乎可以由 $MACs / Peak$ 估算延迟；但在 MPSoC 板级运行中，实际时间还包含权重加载、IFM 打包、DMA 启动、tile 边界同步、缓存重放和 OFM 重排。因此，本文将优化目标定义为降低非计算开销：
\begin{equation}
T_{noncomp}=T_{layer}-T_{compute\_fire}.
\end{equation}
其中 $T_{compute\_fire}$ 表示阵列真正接受一个输出 pixel 计算的周期数，其余部分均属于等待、搬运、反馈或边界开销。

\section{三维分块调度}

本文使用 K 维、输出通道和空间三维分块。K 维分块由 ROWS 决定，最终配置 ROWS=18，因此 $K_{tile}=18$。输出通道分块由 COLS 决定，每列产生两个输出 lane，最终配置 COLS=8，因此 $Cout_{tile}=16$。空间分块由 tile 的输出行范围决定，用于限制片上 IFM/OFM buffer 和单次 AXI DMA 长度。

图~\ref{fig:tiling_schedule} 给出三维调度关系。每个 spatial tile 内，调度器先遍历输出通道块，再对当前输出通道块执行所有 K pass。首个 K pass 从 bias 初始化 partial sum，非首 pass 读取上一轮 partial-PSUM，final pass 输出到后处理流水线。

该调度方式的优点是通用性强，可覆盖从 Conv0 到 Conv9 的不同层形状；缺点是当 $N_{kpass}$ 和 $N_{cout}$ 较大时，pass 边界开销会被重复放大。后续优化均围绕减少这些重复开销展开。

\section{Batch Stream}

早期 per-request 模式中，硬件每需要一个 bias block、weight tile 或 IFM line 时向软件发出请求，软件随后打包数据、启动 DMA 并等待完成。这种方式适合小型 smoke test，但在 Conv6 等真实层中会产生数万次服务事件，A53 侧开销和 DMA 启动开销会淹没阵列计算。

Batch stream 将每个 spatial tile 所需的 bias、weight 和 IFM 数据预先打包成连续 AXI stream。软件在 tile 开始时分别启动三路输入 DMA，硬件通过 packet count 恢复内部边界，只在整个 stream 末尾依赖 TLAST。该方式带来两个直接收益：第一，DMA 启动次数从每个请求一次降低为每个 tile 每类输入一次；第二，AXI backpressure 由 PL 自然吸收，软件不需要在 pass 内频繁轮询硬件请求。

STREAM\_CFG bit0 控制 batch mode。对应的 BIAS\_PACKETS、WEIGHT\_PACKETS 和 IFM\_PACKETS 寄存器用于配置期望 packet 数，硬件完成后通过只读 counter 回报完成数。软件在每个 tile 结束时比较 expected/completed，保证 stream 边界没有丢包或多包。

\section{预打包权重布局}

权重数据天然以模型格式保存，通常按输出通道、输入通道和 kernel 维度组织；而硬件消费顺序是 $Cout block \rightarrow K pass \rightarrow lane \rightarrow channel$。若每次运行时由 A53 重新排列权重，会造成明显的软件时间开销。

本文在构建 Vitis header 时直接生成硬件消费顺序的权重数组。这样 batch mode 下 weight DMA 可以直接读取 ELF 只读段中的连续数组，不再需要运行时 scratch copy 或 repack。PL 端 weight loader 使用 64-bit AXI beat，一拍写入多个 byte bank，进一步降低 weight load 等待。该优化不改变外部 ABI，只改变软件生成数据的排列方式和 PL loader 的内部写入粒度。

\section{Raw-HWC Tile Cache}

IFM 输入存在两种路径。第一种是 prepacked IFM stream：软件提前把每个 K pass 需要的 IFM lane 按硬件顺序打包。该方式 PL 简单，但 A53 侧打包成本较高。第二种是 raw-HWC stream：软件发送自然 HWC tile，PL 在片上缓存后按 pass 和窗口顺序 replay。本文引入 raw-HWC tile cache 以降低后端层的软件打包压力。

图~\ref{fig:raw_hwc_cache} 对比两种路径。prepacked 路径把重排压力放在软件；raw-HWC 路径把重排压力转移到 PL cache/replay，但可减少 A53 逐 pass 复制和索引开销。对 3x3 层，cache materializes 每个输出 pixel 的 3x3 窗口，并按 18 lane 输出给阵列；对 1x1 层，cache 按连续通道向量 replay。

raw-HWC 并非对所有层都收益为正。其收益取决于 tile 容量、输入通道数、replay 吞吐和 compute overlap。本文最终将 raw-HWC 作为后端 Conv4/5/6/8 的主要优化路径；Conv3 raw-HWC 虽然可功能通过，但由于 tile/FIFO 容量和 replay 开销，板级结果不优于推荐配置，因此作为边界分析而非默认路径。

\section{Backend Full-Tile 调度}

Conv5、Conv6 和 Conv8 的空间尺寸均为 $13\times13$。早期调度将这些层拆成 $4+4+4+1$ 行 spatial tile，可以降低片上缓存容量需求，但每个 tile 都需要重复启动 bias、weight、IFM 和 OFM 流程。随着 raw-HWC cache 使用 URAM 扩容，后端层可以使用完整 $13\times13$ tile，从而减少 tile 边界固定成本。

Backend full-tile 的容量条件可近似写为
\begin{equation}
tile\_pixels \times \left\lceil\frac{C_{in}}{2}\right\rceil \le HWC\_CACHE\_DEPTH.
\end{equation}
在最终 full-tile build 中，Conv5/8 需要 $13\times13\times\lceil256/2\rceil=21632$ 个 materialized word，Conv6 需要 $13\times13\times\lceil512/2\rceil=43264$ 个 materialized word。该容量由 HWC cache 的 URAM 实现承担，换取更少的 spatial tile 启动次数。

\section{数据流优化小结}

本章优化的共同目标是减少 $T_{noncomp}$。Batch stream 降低 DMA 启动和软件服务次数；预打包权重消除运行时 weight repack；raw-HWC cache 将 IFM 重排从 A53 移到 PL 并为后续 overlap 创造条件；backend full-tile 降低后端层空间 tile 固定开销。下一章将进一步讨论多 K pass 场景中 partial-PSUM feedback 和 pass-level prefetch 的调度优化。
