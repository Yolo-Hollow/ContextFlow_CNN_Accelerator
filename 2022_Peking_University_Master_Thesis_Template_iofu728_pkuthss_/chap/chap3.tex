\chapter{加速器系统架构}
\label{chap:architecture}

本章介绍本文加速器的系统结构。设计目标不是单独实现一个卷积算子，而是在 MPSoC 上形成从 DDR 图像输入、PS 侧调度、PL 侧卷积计算、OFM 回写到 YOLO decode 的完整运行链路。为此，硬件架构必须同时满足三个要求：第一，卷积核心具备稳定的 INT8/INT32 计算语义；第二，AXI 边界能够承载真实层的数据量和背压；第三，后处理和输出格式能够支持链式推理和板级验证。

\section{系统总体结构}

图~\ref{fig:system_overview} 给出系统级结构。PS 侧 A53 程序负责准备输入图像包、配置寄存器、启动四路 DMA、维护层和 tile 调度，并在每层结束后解析 OFM packet。PL 侧 accelerator 接收 AXI-Lite 配置，通过 bias、weight、IFM 三路 AXI-Stream 输入完成卷积计算，并通过 OFM AXI-Stream 输出 $\{addr,data\}$ debug packet 到 DDR。

控制面和数据面分离是该系统的基本原则。AXI-Lite 寄存器只负责层参数、tile 参数、量化参数、stream 配置和性能计数器；大规模张量数据全部通过 AXI DMA 搬运。这样既避免了 PS 逐字节访问 PL，又使 batch stream、raw-HWC cache 和不同调度开关可以在不改变外部总线结构的情况下演进。

该数据通路采用 packet 化语义。每个输出 pixel 和一个 $Cout_{tile}$ 通道块形成一个 PSUM packet，非 final K pass 写回 partial-PSUM，final K pass 进入后处理流水线。后处理后，每个有效输出 byte 被打包为 OFM debug packet。虽然该输出格式不是最终最高效的连续 HWC burst，但它保留了地址信息，便于软件重排和 golden 比对，是当前板级验证链路的基础。

\section{Systolic 计算核心}

本文最终板级配置采用 ROWS=18、COLS=8、$Cout_{tile}=16$。阵列沿 K 维接收 18 路 IFM lane，每个列位置对应两个输出通道 lane，因此一个 pass 处理最多 16 个输出通道。PE 内部完成 INT8 乘法和 INT32 累加，权重在当前 pass 内驻留，IFM 向量随输出 pixel 推进。

对 3x3 卷积，IFM feeder 负责根据 $oy,ox,k_y,k_x,c_i$ 生成展开后的 K 维向量。对 1x1 卷积，硬件支持 native vector path，避免把 1x1 强行映射为稀疏 3x3 后带来的无效 K pass。这样 Conv7 和 Conv9 检测头可以使用更短的 $K_{total}$，减少后端层调度开销。

\section{后处理流水线}

final K pass 的输出首先进入重量化模块。每个输出通道 lane 有独立的 multiplier、shift 和 output zero point，配置通过 AXI-Lite 间接寄存器写入。重量化后的 uint8 输出进入 activation LUT，支持 identity、ReLU/Leaky ReLU 等运行时可配置语义。若当前层启用 pooling，则 OFM pooling 模块执行 $2\times2$、stride=2 的 maxpool，并将池化后的输出写入 OFM byte stream。

该设计使 Conv0--Conv4 中的卷积和池化可以在 PL 内连续完成，软件看到的层输出已经是下一层输入所需的 HWC 量化张量。对后端不带 pool 的层，后处理路径直接输出卷积结果。

\section{AXI-Lite 配置与性能计数器}

AXI-Lite 寄存器分为四类。第一类是基础层配置，包括 feature map 尺寸、kernel/stride/pad、$K_{total}$、$Cout$、tile 行范围和 expected bytes。第二类是 stream 配置，包括 batch mode、raw-HWC mode、early drain、pass prefetch、continuous PSUM 和 during-compute prefetch 等开关。第三类是量化和 activation LUT 间接写入寄存器。第四类是只读性能计数器，包括 busy、wait、stage、sub-stage、raw-HWC、prefetch、collector 和 pass timeline 统计。

性能计数器是本文实验论证的重要组成部分。它们不改变外部数据格式，却能在每个 tile 或每层结束后解释加速器时间消耗：等待 DMA、feeder replay、compute stage 空泡、PSUM drain、OFM post-process 分别占多少周期。第六章将使用这些计数器说明优化如何改变瓶颈分布。

\section{软件运行时协同}

Vitis bare-metal runtime 使用静态 layer descriptor 描述 Conv0--Conv9 的输入尺寸、输出通道数、kernel、pool、K passes、Cout blocks 和 golden 信息。运行时按 layer 和 spatial tile 循环，写入配置寄存器，启动 OFM S2MM DMA，再启动输入 MM2S DMA，最后等待 accelerator done 和 OFM DMA 完成。

在验证模式下，软件解析每个 OFM debug packet 的地址和数据，将其重排为 HWC buffer，并与 RTL semantic golden 比较。在 DDR image demo 模式下，软件从固定 DDR 地址读取图像包，执行十层硬件推理后对 Conv9 输出运行 YOLO decode。该路径证明本文设计不仅能通过模块仿真，也能在真实 PS/PL 协同环境中完成端到端图像推理。
